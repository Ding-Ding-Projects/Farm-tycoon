# Android build

Farm Tycoon is a dependency-free static web app, so the Android target wraps exactly the same
files the browser and the Electron desktop app run. This document is the handoff: it records what
has been built, what has deliberately **not** been done, and the exact steps and checks that remain.

## Status, stated plainly

| Piece | State |
|---|---|
| Capacitor declared as a devDependency | done |
| `capacitor.config.json`, app id matched to the Electron target | done |
| npm scripts (`android:add`, `android:sync`, `android:build`) | done |
| Keystore material added to `.gitignore` **before** any key exists | done |
| Android launcher icons generated in code (10 PNGs, 5 densities) | done |
| Mobile layout pass, verified at 320x720 and 375x812 | done |
| Native `android/` project generated | **not done** (needs the Android SDK) |
| Release keystore created | **not done** (must be created by the repository owner) |
| APK built | **not done** |
| APK installed and tested on a device | **not done** |

**No APK has been produced, and nothing here should be read as saying the app runs on Android.**
The web layer is verified; the native wrapper is scaffolded and unbuilt.

## The signing exception, recorded on purpose

This project's standing policy is that code signing is skipped everywhere, and the Windows
installer is deliberately shipped unsigned (see `ROADMAP.md`).

**Android is the one exception, and it is not a preference.** Android's package manager refuses to
install an unsigned APK at all, through every route: `adb install`, sideloading, and the Play
Store. Signing is not a distribution nicety there, it is the only way an APK can exist. The
repository owner authorised this exception explicitly, scoped to Android alone.

**It does not generalise.** The Windows target keeps its no-signing rule unchanged. If you are
reading this while working on the desktop installer, nothing here applies to you.

### The keystore is a credential

It is generated by the repository owner, on their own machine, and never by an agent. It is never
committed, never pasted into a chat or an issue, never placed in a command that lands in a log,
never uploaded as a release asset, and **never given to CI**. That last one has a consequence
worth stating: **the signed APK is built locally, not by GitHub Actions.**

`.gitignore` already refuses `*.jks`, `*.keystore` and `keystore.properties`. Those lines were
added before any key existed, so a key cannot be committed by accident even once.

A self-signed certificate is also not acceptable to the Play Store. This produces a **sideloadable**
APK. Release notes must say so rather than implying store distribution.

## What is still required

### 1. Android SDK

Not installed on the build machine at the time of writing (`ANDROID_HOME` unset, no `gradle` on
`PATH`). Installing it requires accepting Google's SDK licences, which is a decision for the
repository owner rather than something an agent should do unattended.

Needed: an Android SDK with platform tools and build tools, and `ANDROID_HOME` set. A JDK is
already present (Temurin 25). Note that very new JDKs sometimes run ahead of what the Android
Gradle Plugin supports; if Gradle complains about the Java version, that is the reason, and a JDK
17 or 21 alongside it is the usual answer.

### 2. Generate the keystore (owner runs this, once)

```
keytool -genkeypair -v -keystore farm-tycoon-release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias farm-tycoon
```

Then create `keystore.properties` beside it, which `.gitignore` already refuses:

```
storeFile=farm-tycoon-release.jks
storePassword=...
keyAlias=farm-tycoon
keyPassword=...
```

### 3. Generate and build the native project

```
npm run android:add      # one time: creates android/ (gitignored, regenerable)
npm run android:sync     # copies the web app into the native project
npm run android:build    # gradle assembleRelease
```

`android/app/build.gradle` then needs a `signingConfigs` block reading `keystore.properties`.
That file is generated by Capacitor, so it is wired after `android:add` rather than committed here.

## Checklist for whoever tests it

Testing and defect-fixing on Android is owned by a separate agent, not by the one that wrote this.
Everything below is unverified and must actually be run on a real device with "install unknown
apps" enabled.

- [ ] `apksigner verify --print-certs` reports the APK as signed
- [ ] The app installs and launches
- [ ] `chrome://inspect` shows zero console errors on boot
- [ ] The world renders, and pans and zooms by touch
- [ ] Pinch-zoom and two-finger pan behave
- [ ] A craft can be queued, played through its minigame, and collected
- [ ] Each of the twelve input families is playable by touch, in particular
      `dual` (two independent values at once) and `drag` (carry and drop), which
      were designed against a mouse and a keyboard
- [ ] The save survives a force-quit and a relaunch
- [ ] Layout holds at the device's real width, including the minigame modal
- [ ] The launcher icon renders correctly at the home-screen size

**A desktop browser narrowed to phone width is not evidence for any touch item above.** It still
has a mouse, it has no on-screen keyboard, and it does not report touch points. The layout items
were checked that way and are marked done above; the touch items were not, and are not.

## Known risks worth checking first

- **`dual` needs two simultaneous touch points.** The shared input layer maps a single pointer to
  one side by its x position, which works with a mouse and works with one finger, but a phone can
  send two. If it feels wrong, that normaliser in `src/minigames/input.js` is where to look.
- **`drag` uses `pointerdown` plus `closest('[data-grab]')`.** Touch drag on Android can be
  intercepted by the WebView's own scroll handling; `touch-action` on the stage may be needed.
- **Dynamic `import()`** is what loads every minigame. It is verified working under Electron's
  `file://`, and Capacitor serves over `https://localhost` instead, which is a different scheme
  again. It should be fine, and it should still be checked first, because if it fails then every
  playable item is unreachable while everything else looks perfect.
